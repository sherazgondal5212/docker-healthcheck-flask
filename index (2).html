Technical workflow

  1. Copied Project 1.1 into 02-docker-healthcheck and kept a backup of its Dockerfile for comparison.
  2. Added PYTHONUNBUFFERED, an explicit uid 1000 for appuser, and a HEALTHCHECK that calls /health with Python's urllib (the slim image has no curl).
  3. Built gda-flask:1.2 and started flask-health.
  4. Checked the status right after start and again after 15 seconds.
  5. Started flask-broken with a health command pointed at port 9999, where nothing listens.
  6. Checked its status, then called its real /health endpoint.
  7. Collected image size, user, logs and Dockerfile, then removed both containers.

Finding: plain Docker only labels a container unhealthy. It does not restart or stop it. Acting on that label is the job of an orchestrator such as ECS or Kubernetes (Phase 4).

Limits: the failure test points the check at a wrong port. It simulates a failed check, not a crashed app. The reason for the Errno 99 error was not investigated, so none is claimed.

Automation scripts breakdown

FileWhat it does
DockerfileBuilds from python:3.12-slim, installs pinned dependencies, creates appuser (uid 1000), adds the HEALTHCHECK, starts Gunicorn on port 5000.
app/app.pyDefines / (reads APP_VERSION) and /health.
app/requirements.txtPins Flask 3.0.3 and Gunicorn 22.0.0.
.dockerignoreKeeps .git, caches and .env out of the build.
docker build -t gda-flask:1.2 .
docker run -d --name flask-health -p 5000:5000 -e APP_VERSION=1.2 gda-flask:1.2
docker inspect --format '{{json .State.Health}}' flask-health

HEALTHCHECK settings: interval 10 s, timeout 3 s, start period 5 s, retries 3. The 10 s interval suits a quick demo; 30 s is common in production.
